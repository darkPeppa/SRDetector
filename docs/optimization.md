# Поиск оптимальных параметров (`srdet optimize`)

Отдельный блок для автоматического поиска лучших параметров детектора и материалов. Исследования
(`srdet study`) меняют один параметр и показывают зависимость. Оптимизация меняет несколько
параметров сразу, сравнивает кандидатов по заданной целевой функции с ограничениями и выдаёт
готовую конфигурацию `best.yaml` с оценкой погрешности.

```bash
docker compose run --rm srdet optimize --list
docker compose run --rm srdet optimize O01_geometry_60keV            # полный бюджет
docker compose run --rm srdet optimize O01 --quick                   # быстрая проверка спеки
docker compose run --rm srdet optimize O01 --set beam.energy="100 keV"
docker compose run --rm srdet optimize O01 --resume runs/optimize/<папка>   # продолжить
docker compose run --rm srdet optimize O02 --archive                 # упаковать в results/
docker compose run --rm srdet run runs/optimize/<папка>/best.yaml    # прогнать найденное
```

## Конструктор в веб-интерфейсе

Страница **Оптимизация → Конструктор** собирает ту же спецификацию, что и YAML ниже, но формами:

1. **Пресет** — любая спецификация из `configs/optimize/` загружается в форму целиком; её можно менять.
2. **Детектор и фиксированные условия** — базовая конфигурация и закреплённые ключи (`set`), например
   `beam.energy = 100 keV`. Ключи выбираются из `defaults.yaml`, с подсказкой и значением по умолчанию.
3. **Свободные параметры** — ключ, тип (диапазон, целые, варианты), границы с единицами, `log`;
   для ключей со списком значений (покрытие, сенсор, материал) — галочки. Параметр без ключа
   «виртуальный»: он нужен только в **вычисляемых** ключах (шаг сот = D + 2·покрытие + стенка).
4. **Цель** — метрика или формула; под формулой показано, что она значит словами, и описание
   каждой метрики. **Ограничения** — строки «метрика, оператор, порог». Фронт Парето и метрики отчёта.
5. **Метод** — выбор кандидатов, кандидатов на первой ступени, события по ступеням, η, уточнение,
   проверка повторами, seed.

Справа при каждом изменении спецификация проверяется (`POST /api/optimize/check`): ошибки
блокируют запуск, предупреждения подсказывают опечатки (неизвестная метрика или ключ, параметр,
который ни на что не влияет, точки с невозможной геометрией). Там же **план**: что будет посчитано
на каждой ступени, сколько симуляций и событий. Кнопки: quick, полный поиск, «сохранить как
пресет» (`configs/optimize/<имя>.yaml`), скачать YAML. Спецификация запуска сохраняется в
`runs/web_configs/optimize/`, результат — как обычно в `runs/optimize/`.

На странице результата вкладка **«метод и цель»** показывает формулу цели словами, параметры с
лучшими значениями и план поиска с фактическим числом испытаний по ступеням. Пока поиск идёт,
вверху виден прогресс (`progress.json`), страница обновляется сама. Кнопка **«В конструктор»**
открывает спецификацию запуска для правки и повторного запуска.

## Формат спецификации

```yaml
name: O01_geometry_60keV
base: full.yaml                      # детектор, от которого начинается поиск
set: {beam.energy: 60 keV}           # фиксированные параметры
space:                               # свободные параметры: короткое имя -> описание
  L:    {path: geometry.length, low: 0.5 mm, high: 5 mm, log: true}
  D:    {path: geometry.channel_diameter, low: 100 um, high: 400 um, log: true}
  wall: {low: 2 um, high: 40 um}     # без path: виртуальный, используется в derived
  coat: {path: optics.coating, values: [Al, Ag, ESR_LUT]}
derived:                             # вычисляемые параметры (базовые единицы mm / keV / deg)
  geometry.pitch: {expr: "D + 2*0.002 + wall", unit: mm}
objective: {expr: "det_yield_per_keV * detection_efficiency", direction: maximize}
constraints: ["psf_r50_um <= 120", "detection_efficiency >= 0.8"]
pareto: {x: psf_r50_um, x_dir: min, y: det_yield_per_keV, y_dir: max}
search:
  sampler: lhs                       # lhs | random | grid
  initial: 24
  events: [300, 900, 2700]           # статистика по ступеням
  eta: 3                             # после ступени остаётся лучшая треть
  refine: {iterations: 4, events: 2700, step: 0.15, min_gain: 0.03}
  final: {top: 3, events: 5000, repeats: 3}
quick: {initial: 6, events: [60, 180], refine: null, final: {top: 1, events: 200, repeats: 2}}
```

* Параметры: непрерывные (`low`/`high`, по желанию `log: true`), целые (`type: int`) и
  категориальные (`values`). Единицы указываются как в конфигах.
* В `objective` и `constraints` пишутся арифметические выражения над метриками (`analysis.metrics`: `lce`,
  `det_yield_per_keV`, `detection_efficiency`, `photopeak_fraction`, `k_escape_fraction`,
  `em_crosstalk`, `optical_crosstalk`, `psf_r50_um`, `psf_in_cell_fraction`, `t_det_median_ns`,
  `det_yield_per_cost`, `resolution_fwhm_poisson_limit`, ...), именами параметров и функциями
  `log, exp, sqrt, min, max, abs`. Если метрики нет или она NaN, кандидат считается недопустимым.
  Выражения разбираются по белому списку (арифметика, сравнения, `and/or`, эти функции); атрибуты,
  индексы и другие вызовы запрещены, поэтому спецификация из веб-интерфейса не может выполнить код.
  Ошибка вычисления (`log(0)`, деление на ноль) делает испытание недопустимым, а не роняет поиск.
* `derived` гарантирует допустимую геометрию: например, шаг вычисляется из диаметра, покрытия и
  стенки. Дополнительно каждая точка проверяется перед запуском: стенка ≥ 1 мкм, не больше 3·10⁵
  сот. Невозможные точки не симулируются и помечаются в `violations`.

## Алгоритм

1. **Отбор**: `initial` кандидатов латинским гиперкубом (по каждой оси ровно одна точка на
   интервал, категории распределены поровну) или полный перебор (`grid`) на малой статистике.
2. **Successive halving**: после каждой ступени остаётся лучшая доля `1/eta` (допустимые
   впереди), и она пересчитывается с большей статистикой и новым seed. Шумные оценки на малой
   статистике отсеивают только явно плохих кандидатов, а решение принимается по точным прогонам.
3. **Уточнение** (`refine`): покоординатный поиск вокруг лучшего по непрерывным параметрам (в
   единичном кубе, с учётом `log`). Шаг принимается, если цель улучшилась больше чем на `min_gain`;
   иначе шаг уменьшается вдвое.
4. **Проверка** (`final`): `top` лучших различных кандидатов прогоняются `repeats` раз с новыми
   seed. В отчёт идут среднее ± стандартное отклонение, а `best.yaml` берётся по результату проверки.

Каждый прогон сохраняется в `trials.csv` с конфигурацией (hash), статистикой и seed. С
`--resume` уже посчитанные испытания берутся оттуда без повторной симуляции (и не дублируются в
`trials.csv`). В `spec.yaml` записывается спецификация вместе с `--set` и фактически
использованным `search` (для `--quick` — быстрым), поэтому продолжение и сканы параметров идут в
тех же условиях. Лучшим всегда становится кандидат, выполнивший ограничения во всех повторах проверки.

## Что получается в папке `runs/optimize/<дата>_<имя>/`

| Файл | Содержимое |
|---|---|
| `report.md` | цель, ограничения, лучшая конфигурация ± σ, таблицы кандидатов, фронт Парето, графики |
| `best.yaml` | готовая конфигурация (`extends: <base>` + найденные параметры), запускается через `srdet run` |
| `trials.csv` | все испытания: параметры, ступень, статистика, все метрики, цель, причина недопустимости |
| `final.csv` | проверенные кандидаты (среднее и σ каждой метрики) |
| `plots/convergence.png` | цель по испытаниям, цвет — ступень, линия — лучший допустимый |
| `plots/sensitivity.png` | цель от каждого параметра: разброс для непрерывных, boxplot для категорий |
| `plots/pareto.png` | фронт Парето по двум метрикам с подписанными кандидатами |
| `runs/` | папки отдельных прогонов (как у `srdet run`) |

## Как писать свою оптимизацию

1. Скопировать спецификацию из `configs/optimize/`, задать `base` и `set`.
2. Сформулировать требования как `constraints`, а не через веса в цели: «r50 ≤ 120 мкм» понятнее и
   устойчивее, чем `yield / psf`.
3. Проверить спеку: `srdet optimize <имя> --quick` (минута), затем полный запуск.
4. Бюджет: число симуляций ≈ initial·(1 + 1/eta + …) + 2·(число непрерывных)·iterations +
   top·repeats. Полный детектор с оптикой — около секунды на 1000 событий при 8 потоках.
